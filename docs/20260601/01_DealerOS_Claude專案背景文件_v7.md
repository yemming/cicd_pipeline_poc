## 第二層：競爭力評估（2026-06-01 新增）

### 2.1 市場現況

台灣重機業目前**幾乎沒有本地化競品**：
- CDK Lightspeed EVO（全球主流）：英文介面、無繁中、無台灣電子發票、無LINE推播、UI被用戶評為「像1990年代做的」、月費昂貴
- 台灣本地：幾乎全數使用Excel、手寫工單或汽車業通用老舊ERP
- **DealerOS唯一的競爭者是「繼續用Excel」這個選項**

### 2.2 DealerOS 真正的強項

1. **功能廣度超越Lightspeed** — 126支頁面，連集團層BSC計分卡和Dealer Health Score都有，Lightspeed沒有
2. **台灣本地化設計** — NT$金額、繁中、Desmo Service、Indian PDC截單時間、LINE推播
3. **重機業專屬邏輯** — PDI整備工單→整車成本、保固舊件管理、雙品牌架構
4. **概念教育做到位** — 庫存管理概念說明+集團管理概念說明文件，幫客戶建立新視界

### 2.3 需要誠實面對的弱點

1. **目前全是假資料** — Partner後端串接進度是簽單關鍵變數
2. **缺少必要模組** — 電子發票（法規）、員工/車型主檔（基礎）、車間派工看板（高頻）
3. **一人推動** — 沒有sales/implementation/客服team，對客戶來說是風險

### 2.4 簽單前最重要的3個API（Partner優先串接）

```
1. GET /api/vehicles?plate=XXXX          → 車牌查詢帶出人車資料
2. GET /api/inventory/alerts?type=below_min → 告警儀表板顯示真實數字
3. POST /api/workorders                   → 工單建立
```
這三個API讓客戶看到「系統是活的」，勝過100支設計精美但假資料的頁面。

## 第四層：工作方式偏好

### 4.1 工作節奏
- 先討論方向，確認後再動手，不急著生成文件
- 一波頁面做完後再一次更新建議書
- 每次任務開始前說明計畫，複雜任務分階段確認

### 4.2 Claude工作順序規則（重要，下次對話必須遵守）

```
正確工作順序（每個模組都要依此執行）：
1. 上網收集業界資料與同業最佳實務
2. 逐頁掃描頁面現況
3. 與SA討論「要不要修改/新增？」→ 取得明確同意
4. 確認異動清單（目錄位置、替換/新增、修改原因）
5. 完成HTML修改/新增
6. 生成MD異動說明文件（含目錄對應、替換/插入標注、API串接點）
7. 生成概念說明文件（如有新概念，供操作說明書參考）
8. 最後寫場景驗證清單.docx

❌ 絕對不能：
- 跳過討論直接動手修改HTML
- 只輸出文件不輸出HTML（每次完成後必須同步present所有產出）
- 場景驗證清單寫在HTML修改之前
```

### 4.3 規則（重要）

```
❌ 金額單位絕對不用 ¥，一律用 NT$
❌ 檔名絕對不放空格，只用中文/英文/數字/底線
✅ 每次 present_files 前先用 ls 確認檔案路徑
✅ D3.js 散佈圖：銷售顧問=圓形，SA/技師=菱形，門店=大圓
✅ 警示橫幅：Phase 1 一律採純規則邏輯，不需 AI
✅ 折扣上下限：手動填寫（非選單），含防呆驗證
✅ 集團功能頁面：每頁標準配置右上角門店切換下拉
✅ 通知機制：提醒SA/主管後由人決定發送方式，非自動發送
✅ 每次完成後：文件+HTML一起present，不要分批
```

## 第八層：重要業務規則（確認版）

### 8.1 售後修護關鍵規則
- Quick Quote三種結果：✅帶入Tab4 / ⏸暫存 / ❌拒絕→人車檔案pending_items
- 通知機制：提醒SA/主管，由人決定發LINE/簡訊/電話（非自動）
- 同一台車有保養+維修：必須開立兩張獨立工單（MN+RP）
- 返工偵測：RP工單開立前比對30天內同類型工單，確認返工→FR付款

### 8.2 庫存管理關鍵規則
- ABC分類盤點頻率：A類月盤/B類季盤/C類年盤
- 再訂購點公式：日均消耗量 × 前置天數 + 安全庫存（Phase 1手動輸入）
- DUCATI PDC截單：下午17:00前送單，隔日上午到貨
- 保固舊件：必須設定到庫位層級，與一般庫存嚴格隔離
- 可用庫存公式：帳面庫存 - RO工單預留 - 調撥在途出庫 + 採購在途入庫

### 8.3 集團管理關鍵規則
- Pace配速公式：（今日累計÷已過工作天）× 本月總工作天 ÷ 月目標 × 100%
- 預測<85%時建議集團介入
- GRP20必須最先設定，是整個系統的安全基礎
- Supabase RLS必須依GRP20角色權限矩陣設定，否則數據安全形同虛設
- org_mode=3（海德生Indian三層）/ org_mode=4（碩文DUCATI四層）
- 促銷活動/定價調整：必須走審核流程，不能繞過

### 8.4 車輛狀態機
```
新車：IN_TRANSIT → PENDING_PDI → AVAILABLE → RESERVED → SOLD
中古車：EVALUATION → PENDING_RECON → AVAILABLE → RESERVED → SOLD
```

### 8.5 核心 API 優先實作順序（簽單前）
```
1. GET /api/vehicles?plate=XXXX              → 車牌查詢（簽單關鍵）
2. GET /api/inventory/alerts?type=below_min  → 告警儀表板（簽單關鍵）
3. POST /api/workorders                       → 工單建立（簽單關鍵）
4. POST /api/vehicles/batch-arrival-confirm  → 到港確認，觸發PDI工單
5. PATCH /api/workorders/{id}/complete       → PDI完工，車輛→可售
```
