# 報告一：跨公司調撥記帳（INTER_COMPANY_TRANSFER）— 事實分離現況確認

**日期：2026-06-20　｜　Partner AI Agent → Russell Hung**
**對應：6/19 裁示 §一**

---

## 結論先講：☑ 是，現有設計已經是「只記事實、不綁會計」

調撥的成本資料**已經跟記帳邏輯分開**。系統只記錄「誰調貨給誰、什麼時候、什麼品項、多少量、什麼成本」這個事實，沒有在資料層綁定任何會計科目或入帳判斷。底下列證據。

這跟保固理賠那次「DealerOS 只記事實、會計判斷交給未來系統」是**同一套設計**，本模組從建表時就已經這樣做，不需要補做改造。

---

## 一、調撥不是獨立的「跨公司」表，而是 `stock_transfers` 的一種情境

DB 裡跟調撥有關的表有三張：

| 表名 | 用途 |
|------|------|
| `stock_transfers` | 零件／耗材跨倉調撥（主表） |
| `stock_transfer_lines` | 調撥明細行 |
| `vehicle_transfers` | 整車跨倉調撥（獨立業務） |

**系統裡沒有任何 `inter_company_transfers` / `intercompany_*` 表。** 「跨公司」不是另存一張表，而是透過「倉庫 → 組織 → 法人（subsidiary）」推導出「這筆調撥是否跨 subsidiary」。這個推導是**執行期算的**（收貨當下才判斷），不是建單時就寫死一個欄位。

---

## 二、`stock_transfers` 整張表沒有任何會計欄位

逐欄查過，`stock_transfers` 只有物流事實欄位：

- **誰**：`source_warehouse_id`（調出倉）、`target_warehouse_id`（調入倉）、`shipped_by` / `received_by`（操作人）
- **什麼時候**：`ship_date`、`expected_arrival_date`、`actual_arrival_date`、`shipped_at`、`received_at`
- **多少**：`qty_requested_total` / `qty_shipped_total` / `qty_received_total`
- **流程狀態**：`status`（draft / in_transit / partial / received / cancelled）— 這是**物流狀態**，不是會計過帳狀態
- **物流**：`logistics_provider`、`logistics_tracking_no`
- 其他：`tr_no`（單號）、`transfer_type`、`reason`、`notes`、作廢欄位、外部對接欄位、`metadata`

**完全沒有** `gl_account` / `account_id` / `journal_entry_id` / `debit` / `credit` / `recognized` / `posted` 任何一個「該記哪個科目、該不該認列」的判斷欄位。

明細表 `stock_transfer_lines` 同理，只有 `item_id`、`qty_*`、`uom`、`unit_cost`。其中 `unit_cost` 是**調撥當下從移動平均成本（`stock_items.unit_cost`）拍下的快照**——這是「這批貨在移動時值多少錢」的成本**事實**，不是「該記到哪個 GL 科目」的判斷。任何外部會計系統都能直接拿這個數字去入帳，不需要 DealerOS 預先替它決定科目。

`vehicle_transfers`（整車調撥）也一樣沒有 GL 欄位；它的 `freight_type` / `freight_amount` 是運費怎麼計入整車成本的**計算事實**，不是會計科目綁定。

## 三、會計判斷被刻意留在「動作層」，不寫進資料

唯一碰到「會計」字眼的地方在 `src/domain/transfers.ts` 的 `receiveTransfer()`（收貨入庫）：

```
（src/domain/transfers.ts ~L1301–1336，收貨 Step 7）
讀 warehouse → org → subsidiary 推導雙方法人：
  同 subsidiary → 標記 stock_receipts.gl_posted = true（內部移倉，無需跨公司分錄）
  跨 subsidiary → gl_posted 維持 false + console.warn「INTER_COMPANY_TRANSFER 未實作」
```

關鍵在於：**這個「同／跨」判斷是收貨當下用推導鏈即時算的，不是建調撥單時就決定並存進欄位。** DealerOS 本身在這裡**沒有**去算「該借哪個科目、貸哪個科目」，只是留下一個「跨公司，未來的會計系統要處理」的標記與提示。前端 detail page 也明文顯示給使用者看：「需走 INTER_COMPANY_TRANSFER 分錄（未實作），收貨不會自動產生 GL JE，會計需手動補」。

這正是裁示要的方向——**事實歸 DealerOS、入帳判斷留給未來確定的會計系統**。

## 五、一個誠實的灰色地帶（不影響「已分離」結論）

`stock_receipts`（收貨單，調撥收貨時產生）這張表有 `gl_posted`（boolean）+ `gl_posted_at` 兩欄，被 `receiveTransfer()` 拿來當「這筆收貨事件的 GL 處理是否已完成」的旗幟。

- 這個旗幟存在「收貨事件表」，**不在調撥表本身**；語意是「已完成 GL 標記」這個**事實**，不是「該記哪個科目」的判斷，仍屬事實層。
- 但它目前只是個 boolean 旗幟，**沒有** `journal_entry_id` 可回指實際分錄。未來真的補 INTER_COMPANY_TRANSFER 邏輯、要做 GL 對帳追溯時，會需要在 `stock_receipts` 增一欄 `journal_entry_id`（指向外部／未來會計系統產生的分錄編號）。

這不是現在的缺陷，只是標記「未來接會計系統時的銜接點」——而且這一欄屆時存的也是「事實」（哪張分錄對應這筆收貨），不是判斷邏輯，跟本裁示原則一致。

---

## 六、本項處置

**結案，無需補件。** 現有設計已符合「只記事實、不綁特定會計系統」的原則，與保固理賠同一套方向。未來若接會計系統，唯一的銜接動作是在 `stock_receipts` 加一個 `journal_entry_id` 回指欄（仍為事實欄），不需要回頭改調撥表的設計。
