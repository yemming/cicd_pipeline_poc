# DealerOS 導入方法論 — 通用導入手冊 v1.0

> 適用對象:任何要導入 DealerOS 的車商客戶(單店 / 多門店 / 多法人集團)。
> 用途:售前報價、SOW 撰寫、專案排程、上線驗收的共用 playbook。
> 維護:本文件是**通用範本**;針對特定客戶的導入計畫請另開 `docs/proposals/onboarding-{客戶}-{date}.md`,不要改本檔。
> 版本:v1.0(2026-05-26)

---

## 0. 核心原則(讀完這節就懂整本手冊的邏輯)

導入專案有兩種視角,**千萬不要混用**:

| 視角 | 是什麼 | 用途 | 在本手冊的角色 |
|---|---|---|---|
| **營運實施視角** | 主檔 → 採購付款 → Order to Cash → 結帳 | 排「誰依賴誰、先上什麼」的施工順序 | **施工骨架(主軸)** |
| **八大循環視角** | 銷售收款/採購付款/生產/存貨/薪工/融資/固資/投資 | 盤點「資金流有沒有漏」、驗收對帳 | **驗收 checklist(不是施工圖)** |

**三條第一性原理,解釋為什麼用營運視角當主軸:**

1. **八大循環假設主檔已存在。** 銷售循環第一步就要拉客戶、品項、價格 —— 那是主檔。所以主檔天生必須先做,「跟著循環走」順序上自相矛盾。
2. **八大循環有一半格子 DMS 不填。** 薪工/融資/固資/投資/研發對車商 DMS 是空白或邊緣,拿它當主軸會把力氣花在錯的地方。
3. **客戶價值與風險都偏好「一個完整營運迴圈先跑通」。** 與其八大循環各做 1/8,不如讓「採購→入庫→維修領料→開單收款」整圈先在真機跑通。

> 一句話:**主檔優先,交易循環按依賴排,八大循環留到結帳層當對帳的尺。**

## 1. 導入專案生命週期(外層方法論)

```
售前 PoC → 合約/SOW → Kickoff → 藍圖 & Fit-Gap
   → 系統設定/客製 → 資料移轉 → 教育訓練 → UAT
   → Cutover 上線 → Hypercare → 結案驗收
```

| 階段 | 主要產出(Deliverable) | 負責方 | 退出條件(Exit Criteria) |
|---|---|---|---|
| **售前 PoC** | Demo 環境、可行性評估 | 我方 | 客戶看到關鍵動線、願意進合約 |
| **合約 / SOW** | 工作說明書、scope、報價、時程、付款里程碑 | 雙方 | 簽約 |
| **Kickoff** | 專案章程、聯絡窗口、溝通節奏、里程碑日曆 | 雙方 | 雙方 PM 確認 |
| **藍圖 & Fit-Gap** | 流程對照表(現況 ↔ DealerOS)、客製清單、scope 凍結 | 我方主導 | scope 凍結簽核 |
| **系統設定 / 客製** | 設定好的環境、客製功能 | 我方 | 內部 SIT 通過 |
| **資料移轉** | 主檔 + 期初餘額灌檔、預演兩次 | 雙方 | 對帳平、客戶確認資料正確 |
| **教育訓練** | 按 persona 的訓練、操作手冊 | 我方 | 各 persona 通過練習 |
| **UAT** | 客戶用**真實單據**驗收、缺陷清單清零 | 客戶主導 | UAT 簽核 |
| **Cutover 上線** | 切換計畫、上線檢核表、回退方案 | 雙方 | 系統正式營運 |
| **Hypercare** | 密集支援(2–4 週)、缺陷快修 | 我方 | 穩定、轉常態維運 |
| **結案驗收** | 驗收文件、知識移轉、維運合約 | 雙方 | 驗收簽核 |

### 1.1 藍圖 & Fit-Gap 是 scope 的真正來源

拿客戶現況流程逐項對 DealerOS 現有功能,每項標四選一:

- **Fit(直接用)** — 現有功能即可
- **Config(設定即可)** — 改設定/主檔/權限就能滿足
- **Gap-客製** — 要開發(走 `spec-to-feature` skill 落地)
- **Out(暫不做)** — 本期不納入,記錄為未來迭代

> ⚠️ scope 來自 Fit-Gap,**不是抄八大循環**。Fit-Gap 凍結後才報固定價;沒凍結就報價=無底洞。

### 1.2 Cutover 策略(三選一,一人維運強烈建議分模組)

| 策略 | 說明 | 適用 | 風險 |
|---|---|---|---|
| **Big-bang** | 全模組同日切換 | 小型單店、流程簡單 | 高,出事範圍大 |
| **分模組(推薦)** | 零件+庫存先上 → 服務 → 新車銷售 → 結帳 | 多數車商、一人維運 | 低,可控 |
| **平行雙跑** | 新舊系統同時跑一段時間 | 對帳要求高、不能斷 | 成本高,雙倍輸入 |

## 2. 功能上線順序(內層施工骨架)

四層,按「資料依賴 + 客戶價值 + 上線風險」排序。

### Layer 0 — 基礎 / 維度(專案啟動就拍死)

```
法人(統編/帳本/本位幣) → 品牌 → 門店 → 部門 → RBAC 角色 → 通知通路(LINE)
```

⚠️ **五軸維度模型必須在這層定案**,因為它是會計分錄與資料隔離(RLS)的地基:

| 軸 | 性質 | DealerOS 表 |
|---|---|---|
| 集團 (group) | 虛 / Tenant 邊界 | `groups` |
| 品牌 (brand) | **虛**(行銷層,不掛統編) | `brands` |
| **法人 (subsidiary)** | **實**(統編 / 帳本 / 本位幣) | `subsidiaries` |
| 門店 (store) | 實 / 營運點 | `organizations` (level=2) |
| 部門 (department) | 虛 / 成本中心 | `departments` |

> **記住 brand ≠ subsidiary。** 法人才掛統編和帳本,品牌是行銷層。多法人集團這裡定錯,後面整套會計全錯。

### Layer 1 — 主檔(名詞:所有交易的前置依賴)

依賴順序:

```
組織/部門 → 員工 & 角色 & 技師 → 會計科目(COA)+ 維度
         → 品項/車型 → 客戶 → 供應商 & 供應商定價
```

| 主檔 | DealerOS 模組 | 備註 |
|---|---|---|
| 組織 / 部門 | 集團組織管理 | Layer 0 已建骨架,這裡補細節 |
| 員工 / 角色 / 技師 | 員工主檔 + 員工角色主檔 | `role_codes` 系統角色 vs `position` HR 職稱分層 |
| 會計科目 + 維度 | COA / gl_dimensions | 五軸維度對映 NetSuite |
| 品項 / 車型 | 品項主檔(parts/setup/items) | 零件 + 整車 |
| 客戶 | 客戶主檔 / CRM | |
| 供應商 / 定價 | 供應商主檔 + 供應商定價 | |

> **主檔絕對先行 —— 這是營運視角與八大循環唯一沒分歧的地方。**

### Layer 2 — 交易循環(動詞:這裡才輪到「採購付款 / O2C」)

按依賴排,**每個迴圈在真機跑通再上下一個**:

```
① 採購到付款 (P2P)   採購單 → 收貨 → 入庫 → 應付 → 付款       ← 先建立庫存
② 庫存管理            調撥 / 盤點 / 期初餘額                    ← 銷售前必須有正確庫存
③ 服務 / 維修(生產) 預約 → 工單 → 領料 → 竣工 → 開單 → 收款  ← 車商最高頻,建議優先
④ Order to Cash       報價 → 銷售訂單 → 交車 → 應收 → 收款      ← 新車營收引擎
⑤ 中古車              估價 → 收購 → 整備 → 庫存 → 銷售
```

**排序理由:**

- **P2P 先於 O2C**:沒進貨就沒庫存,銷售/維修領料都會卡 —— 純依賴關係。
- **維修(③)建議先於新車銷售(④)上線**:維修天天發生、最高頻,先跑通它讓客戶「離不開系統」;新車頻率低、單筆大,可稍後。
- 每個迴圈跑通就同時驗證了**主檔 + 交易 + 會計**三層串得起來。

### Layer 3 — 總帳 / 結帳 / 報表(八大循環在這裡收口)

```
GL 過帳 → 月結 → 財務報表 → NetSuite 對接
```

> **這才是八大循環的正確用法:** 前面每個交易循環產生的分錄,在這層驗證能正確結到財報。用八大循環當「對帳清單」逐項打勾,而不是當施工順序。

### Layer 4 — 上線後 = DealerOS 的獨門賣點

DealerOS 的 **Feedback / CI-CD pipeline 模組**本身就是內建的 Hypercare + 持續改善管道:

```
客戶 /feedback/tickets/new 許願 → LINE 秒推到負責人手機
   → 決定是否啟動開發 → PR → 人工審批 merge → Zeabur 自動部署 → released
```

一般 ERP 導入完進入漫長的「需求單→報價→排程」泥沼;DealerOS 把售後改善**工業化**。售前談判時,這應作為核心 differentiator,不是附屬功能。

## 3. 八大循環 ↔ DealerOS ↔ 上線層 對照表(驗收用)

結帳驗收時逐列確認資金流有沒有正確收口:

| 八大循環 | DealerOS 主場? | 對應模組 | 上線層 |
|---|---|---|---|
| 銷售及收款 (O2C) | ✅ 核心 | sales / quotation / sales-order | Layer 2 ④ |
| 採購及付款 (P2P) | ✅ 核心 | parts/purchase / 收貨 / 應付 | Layer 2 ① |
| 生產循環 | ✅ 核心(維修工單、中古整備) | service/workorders / usedcar | Layer 2 ③⑤ |
| 存貨與倉儲 | ✅ 核心 | inventory / 調撥 / 盤點 | Layer 2 ② |
| 薪工循環 | ⚠️ 邊緣(只有組織/員工主檔) | employees / roles | Layer 1 |
| 融資循環 | ❌ 初期不做(分期/車貸看需求) | — | Out |
| 固定資產 | ❌ 走 NetSuite / 總帳 | — | Layer 3 / 外部 |
| 投資 / 研發 | ❌ DMS 非主場 | — | Out |

> **觀察:八大循環裡只有前四個是 DMS 真主場。** 這正是「不該用八大循環當施工骨架」的鐵證 —— 一半格子是空的。

## 4. 三個決定成敗的實務雷點

1. **期初餘額(opening balance)是導入死活。**
   庫存期初量、AR/AP 未結餘額、GL 期初餘額。資料髒、對不平,上線第一天就崩。
   → **排「資料移轉預演」至少兩次**,每次都做對帳。

2. **教育訓練按 persona 切,不要一份大全套。**
   倉管只學收貨/盤點、SA 只學工單、會計只學結帳、業務只學報價/訂單。
   → 每個 persona 一份精簡 SOP + 一次實機練習。

3. **UAT 用客戶的真實單據,不要用造的 fixture。**
   用他上個月真的採購單/工單/銷售單跑一遍,客戶才會信、才驗得出邊角缺陷。

## 5. 階段檢核表(可直接複製到專案計畫)

### Kickoff 前
- [ ] 客戶 profile 確認:單店 / 多門店 / 多法人集團
- [ ] scope 含不含總帳財報、NetSuite 對接
- [ ] 現用什麼系統(資料移轉來源)
- [ ] 法人/帳本/本位幣清單

### Layer 0 基礎
- [ ] 五軸維度定案(group/brand/subsidiary/store/department)
- [ ] RBAC 角色與權限矩陣
- [ ] LINE 通知通路接好、測試推送成功

### Layer 1 主檔
- [ ] 組織/部門、員工/角色/技師
- [ ] COA + 維度對映
- [ ] 品項/車型、客戶、供應商/定價
- [ ] 主檔資料移轉對帳通過

### Layer 2 交易循環(逐迴圈)
- [ ] P2P 跑通(採購→收貨→入庫→應付→付款)
- [ ] 庫存(調撥/盤點/期初)對帳平
- [ ] 維修工單跑通(預約→工單→領料→竣工→開單→收款)
- [ ] O2C 跑通(報價→訂單→交車→應收→收款)
- [ ] 中古車(視 scope)

### Layer 3 結帳
- [ ] GL 過帳正確
- [ ] 月結流程跑一輪
- [ ] 財務報表對得起來
- [ ] NetSuite 對接(視 scope)
- [ ] 八大循環對照表逐列打勾

### Cutover & 上線後
- [ ] Cutover 策略選定 + 回退方案
- [ ] 上線檢核表
- [ ] Hypercare 期間(2–4 週)缺陷追蹤
- [ ] Feedback pipeline 開放給客戶許願
- [ ] 結案驗收簽核

## 6. 怎麼用這份手冊接一個新客戶

1. 複製本檔的骨架到 `docs/proposals/onboarding-{客戶}-{date}.md`(**不要改本通用範本**)。
2. 跑 §1.1 Fit-Gap,把 scope 凍結。
3. 按 §2 四層排專案時程。
4. 客製需求走 `spec-to-feature` skill 落地。
5. 結帳驗收用 §3 對照表 + §5 檢核表。
