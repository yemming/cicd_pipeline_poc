## Item 1：TL 借料走正式 repair-pick 倉管領料流程

### 1.1 為什麼原本走不通（根因）

repair-pick 倉管領料的「待領料工單」清單與領料預覽，**完全以 `work_orders` +
`work_order_items(kind='parts')` 驅動**，不認 `repair_orders`：

- 清單：`listPendingPartsWorkorders()` — `src/domain/issues.ts:632`
  查 `work_orders`（status ∈ draft/dispatched/in_progress/qc）→ join `work_order_items`
  kind='parts' → 排除已領料完成者。
- 領料預覽：`previewRepairPick()` mode='ro' — `src/domain/issues.ts:848`
  從 `work_order_items` kind='parts' 算需求數量、跑 FIFO 配置。
- 過帳：`persistPick()` — `src/domain/issues.ts:1107`
  寫 `stock_issues`（`ro_id` FK → **work_orders.id**）、扣 `stock_items`、認 COGS。

而 TL 借用測試工單是一筆 `repair_orders`（prefix_p1='TL'），**建立時不會產生對應的
`work_orders`**（除非共用 appointment_id 被動回填，`repair-order-actions.ts:436`）。
因此 TL 永遠不出現在倉管的領料清單 → 上一版才走了 tl-close 自行逐行處置的捷徑。

> 橋接欄位 `work_orders.repair_order_id` 早在 C-28（migration `20260609030104`）已建，
> 但只被動靠 appointment_id 回填，對「TL 內部借用」這種沒有 appointment 的情境無效。

### 1.2 補做的橋接

新增 domain helper **`syncTlWorkOrderBridge(roId)`** — `src/domain/work-orders.ts`：

1. 驗 RO 為 TL + 同 brand；TL 必須已綁測試車輛（`vehicle_id`），否則擋下回報。
2. 讀該 TL 當前借料明細（`repair_order_lines` kind='part' 且綁 item_id、qty>0）。
3. 以 `repair_order_id` 為鍵 **upsert 一筆 `work_orders`**（冪等）：
   `status='dispatched'`、`ro_no=ro_code`、`external_source='tl_bridge'`、
   `metadata={is_tl:true, source:'tl_bridge'}`、`customer_id` 取自 RO（TL 內部借用為 NULL）。
4. 依當前借料明細**全量重建 `work_order_items(kind='parts')`**（只動本橋接工單的 parts 行）。

橋接後，TL 工單自然滿足清單三條件（dispatched + 綁 parts + 未領料）→ 進倉管待領料清單；
倉管選工單 → 系統跑 FIFO 配置 → 倉管確認過帳（persistPick 扣庫、記 `stock_issues`、認 COGS）。
**零件出庫從此必經倉管之手，有 `stock_issues` GI 單可稽核。**

### 1.3 觸發點（讓橋接自動且同步）

| 觸發 | 檔案:行號 | 行為 |
|------|-----------|------|
| TL 工單確認建立 | `repair-order-actions.ts` confirm 成功區塊（prefix_p1==='TL'） | 建橋接工單殼（明細後加，故先建殼） |
| 新增借料明細 | `repair-order-line-actions.ts` `addPartLineAction` | TL 則 re-sync 橋接 work_order_items |
| 修改借料明細 | 同檔 `updatePartLineAction` | 同上 |
| 刪除明細 | 同檔 `deleteLineAction` | 同上 |

實作：`ensureRoOwned()` 改為一併回傳 `prefix_p1`；新增 `resyncTlBridgeIfNeeded(roId, prefix_p1)`
（非 TL 不動、失敗只記 log 不阻斷主流程）。

> 設計理由：閘門頁是「先建單、明細後加」，所以 confirm 當下橋接工單可能尚無料件
> （不會出現在清單，符合預期）；SA 一旦加借料明細，re-sync 即把明細同步到橋接工單，
> 倉管立刻在 repair-pick 看到正確的借料數量。

## 澄清一：取消到倉管確認之間，stock_item 的中間狀態

### 機制

走正式 repair-pick 後，TL 借料的庫存生命週期是：

```
倉管 repair-pick 過帳（persistPick）
  → stock_items 該 lot qty 扣減，扣到 0 時 status='issued'（料件實體已離庫房）
  → 寫一筆 stock_issues GI 單（ro_id = 橋接 work_order）可稽核

TL 結案 tl-close「退回庫房」
  → 建一筆 parts_return_requests（status='pending'，待倉管確認）
  → 此時庫存「不」立即回補

倉管在 return-in 確認收到（confirmReturnRequestAction）
  → insert 一筆全新 available stock_item 回補（metadata 記 source_ro_id / return_request_id）
  → parts_return_requests.status='confirmed'
```

### 直球回答貴方的問題

> 「在『取消』到『倉管確認』之間，那批 stock_item 的狀態是什麼？」

那批已出庫的 lot 維持 **`issued`**（qty 0）；同時有一筆 `parts_return_requests`
（`status='pending'`）作為「預期退回、待倉管確認」的可見記錄。

> 「如果仍顯示 issued，庫存報表在這段期間會顯示料件還在外面，與實際不符？」

我方認為這在物理上是**相符**的：料件確實還在外面（技師手上 / 退回途中），**尚未實際回到
貨架**。庫存報表此時顯示它「不在可用庫存」是正確的——零件未經倉管實體點收前，不該被
當成「已回庫、可再發」。`parts_return_requests` 的 pending 記錄正是這段期間的可見性機制
（「這批料預期會回來、倉管尚未點收」），帳面與實物的對齊點是**倉管實體確認那一刻**，
而非結案決定那一刻。這與「零件進出必經倉管」的原則一致：回庫也要倉管點頭才算數。

> 若貴方希望在庫存查詢另立一個明確的「退料在途（return_pending）」可視狀態（而非沿用
> issued + pending 退料單），這屬於庫存報表的展示層強化，我方可另開規格提案，等貴方裁示
> 再做——不自行決定。

### 補充：為何沒用 `stock_items.status='return_pending'`

出庫流程 `persistPick`（`issues.ts:1204`）扣庫時未在 stock_item 寫
`metadata.source_ro_id/source_addon_id`，事後無法可靠回溯「是哪張工單出的哪個 lot」。
故「庫存回補」不採「翻舊 issued lot 改 return_pending」，改採與既有 `parts-return-in`
一致的做法：倉管確認時 insert 一筆全新 available lot。最終庫存數字正確，且回補有倉管點收
的稽核記錄。此決策已記在 `src/domain/parts-return-requests.ts` 檔頭註解。
