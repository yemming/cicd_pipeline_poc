## 必須補做項目一：TL 借料必須走正式 repair-pick 流程

### Partner 的做法

> 「TL 結案頁直接讀工單 repair_order_lines 逐行處置，demo 閉環完整；若要 TL 走 repair-pick 正式領料需補 work_orders 橋接（非閉環關鍵、未做）。」

### 我方的立場

**這個判斷不是你有權自行做出的。**

「非閉環關鍵」是你的技術評估，不是業務事實。

倉管是零件庫房的**絕對管理人**。任何零件的進出，不管是正式維修、追加項目、還是 TL 借用測試，都必須經過倉管的點頭和簽核。這不是流程設計的偏好問題，而是**責任歸屬的基本原則**：

- 零件出了庫房沒有倉管的紀錄，出了問題誰負責？
- 技師說借了3個，倉管說從沒看過，系統顯示什麼？
- 盤點時帳面和實物對不上，要往哪裡查？

指令文件已經明確寫出：
> 「TL 工單開立後才能到 `/parts/issue/repair-pick` 正常領料」

這句話的「正常領料」，意思就是走現有的倉管發料流程，不是另開一條沒有倉管的捷徑。

我方承認指令在這一點上沒有詳述業務原由，這是我們下一版指令會改進的地方。但技術困難（work_orders 橋接）不是跳過業務流程的理由。正確做法是遇到困難停下來回報，讓我方決定怎麼處理，而不是自行裁量「這個不重要，跳過」。

### 要求

補做 `work_orders` 與 `repair_orders` 的橋接，讓 TL 工單能夠正常走 `/parts/issue/repair-pick` 領料流程，倉管必須參與發料確認。

完成後提供：
- 橋接的實作說明
- 倉管在 repair-pick 看到 TL 工單的截圖

## 必須補做項目二：DB constraint 修改必須有 migration 記錄

### Partner 的做法

報告提到：
> 「`repair_orders_prefix_p1_check` 原不含 TL → 已 ALTER 加入」

這筆 ALTER 是直接在正式站資料庫執行的，codebase 裡沒有對應的 migration 檔案。

### 我方的立場

**這是工程規範問題，不是小事。**

直接修改正式站資料庫而不寫 migration，帶來的風險是：

- 下次重新部署或建立新環境，這條 constraint 不見了，TL 工單建不起來
- 沒有人知道這個 constraint 是什麼時候改的、為什麼改的
- 無法回溯、無法稽核、無法重現

這套系統**不是學生作業**。它是一套準備向客戶收費、在正式營業環境運行的商業軟體。在這個層級的系統裡，所有 DB 結構變更都必須有版本記錄，這是最基本的工程紀律。

程式碼可以優化、可以簡潔，但**涉及流程控制、行為稽核、資料結構的地方，不能為了省事走捷徑**。一旦出問題，追查成本遠高於當初多寫一份 migration 的時間。

### 要求

補寫 `repair_orders_prefix_p1_check` 的 migration 檔案，納入 codebase 版本控制。

完成後提供：
- migration 檔案的路徑與內容
- 確認 migration 已 apply 且 codebase 與正式站 DB 狀態一致

## 關於「stock_items.status 不採 return_pending」

這個技術選擇的最終結果（庫存數字）是正確的，但有一個問題沒有說清楚：

**在「取消」到「倉管確認」之間，那批 stock_item 的狀態是什麼？**

如果仍然顯示 `issued`，那麼庫存報表在這段期間會顯示那批料件還在外面，與實際情況不符。

請在補做回覆中說明這段期間的中間狀態如何處理。
