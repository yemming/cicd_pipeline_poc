## 盲測前 ①：缺貨情境 — 結論為**可能性 A**（逐項偵測、整單卡死、雙層守門）

### 一、現況實際邏輯（讀碼 + 真實 e2e 雙重確認）

倉管領料(repair-pick)採「預覽配置 → 過帳」兩步：

1. **預覽階段 `previewRepairPick` 會逐項檢查庫存**：對每一項零件分別跑 FIFO 配置（`stock_items` available qty），算出 `shortage = max(0, 需求 − 可配)`。
2. **只要任一項 `shortage > 0`，整張 `can_post = false`**。
3. **前端**「一鍵領料並過帳」按鈕 `disabled`，並顯示紅色「庫存不足」badge + 缺料明細 + 「建立補貨需求單 / 通知售後 SA 啟動增項閉環」入口。
4. **後端** server action `pickForWorkOrder` 過帳前**再跑一次** `previewRepairPick`，`!can_post` 直接 `return { ok:false, error:"庫存不足，無法過帳" }`。

→ **不存在** B（沒檢查、負庫存／拋錯）或 C（只出有貨、跳過缺貨）的路徑。**確定是 A。**

### 三、「分批出庫不存在」結論成立

## 盲測前 ②：其他工單類型「中間地帶缺口」盤點表（如實回報、未自行排優先度）

> 問題定義：零件出庫之後、到該單據真正結束之前，是否存在「會被忽略、沒有任何一方（售後/倉管/財會）主動追蹤」的中間地帶。

| 工單類型 | 是否存在中間地帶缺口 | 缺口具體說明 |
|---|---|---|
| 一般 RO 維修工單（付費） | **部分存在** | 零件出庫後到結帳之間，**僅 SA 角色**的「我的待辦」有 `待結帳` 提醒、售後首頁有 `awaiting_checkout` 聚合 KPI；**倉管、財會無對應追蹤**，無應收帳款老化(AR aging)視圖，SA 若忽略待辦**無升級(escalation)機制**。零件成本已扣、費用懸空，只靠單一角色主動盯。 |
| 一般 RO 維修工單（保固免費） | **存在** | `已關閉-保固待確認` 是終態，但此狀態**未進任何人的待辦、未進任何 KPI 卡**；且此終態到 `已關單` 的轉換目前在狀態機中被停用。零件已出庫、工單已進終態，但「保固核銷 vs 公司自付」的費用歸屬懸而未決，**無任何角色能從清單或提醒感知到這批單的存在**。 |
| 保固索賠工單 | **存在** | 索賠申請(`parts_warranty_claims`)與維修工單(`repair_orders`)是**脫鉤的手動流程**：無外鍵、無自動 trigger，SA 出庫後須**人工**另建 claim 才進 SLA 追蹤；若漏建，零件成本從關單到原廠核銷之間**完全無人追蹤**。SLA 倒數只作用於「已建立」的 claim。 |
| 調撥出庫 | **不存在顯著缺口** | 出庫後 `stock_items.status='in_transit'`；`/parts/operations/transfers-in-transit` 有「逾期未入庫(delayed)」KPI（`expected_arrival < today 且 已收 < 已出`），目標倉管可在「調撥入庫」頁看到在途待接收。全程有角色可見。 |
| 內售出庫 | **存在（款項面）** | 出貨面有 `delivery_status`(pending/in_transit/delivered) + 在途 KPI；**但款項/應收面完全空白**：內售列無任何 payment 欄位、`stock_issues` 無 AR 關聯、無「內售待收款」待辦、無 `ar_invoices` 外鍵。出庫後買方欠款是否到期/已付，系統無從感知。 |
