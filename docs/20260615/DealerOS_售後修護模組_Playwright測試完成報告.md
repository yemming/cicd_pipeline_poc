## 執行方式說明（重要，務必先讀）

原始測試腳本是「理想版測試計畫」，與實機有兩處落差，**無法逐字執行**，故做了以下對應調整（已驗證為事實）：

1. **腳本的 `data-testid` 全為虛構** —— 比對實機原始碼，`walkin-plate-input`、`email-input`、`login-btn`、`add-dispute-btn`、`audit-timeline`…**一個都不存在**（app 實際的 ~60 個 data-testid 命名完全不同，連 `login()` helper 都跑不起來）。→ 改用**真實 DOM 的文字 / role 選擇器**驅動。
2. **帳號為 placeholder**（`sa@dealeros-test.com` / `TEST_SA_PWD`，腳本註明「由 Ming 填入」）。→ 改用**真實非 admin e2e persona**：`e2e-sa`（SA）、`e2e-aftersales_lead`（售後主管）、`e2e-tech`（技師）、`e2e-warehouse`（倉管），scope = Indian。
3. **執行範圍：非破壞性驗證**（依 Ming 指示）——M 系列完整閉環會在正式站寫入真實單據（建臨時進廠 / 收款 / 關單等不可逆動作），故本輪**只跑到「不可逆寫入前」**：導航、開表單 / Modal、切 Tab、唯讀查詢、驗證 UI 狀態並截圖；**不做** payment / 關單 / 派工 / 建立持久化單據。這是 UI 流程**狀態驗證**，非真實 mutation e2e。

## 特別說明（誠實揭露）

1. **本輪是 UI 狀態驗證，非完整 mutation e2e**（Ming 選非破壞性）。要做真實閉環（含收款/關單寫入正式站 Indian 資料），需另行授權；屆時可把本腳本的「開表單即截圖」改為「填值→提交→等結果」。
2. **B2 損傷異議不可修改**：以 DB 結構證明（無 update/delete policy）為主要證據，UI 僅截到區塊（草稿 PI 無已標記損傷時，逐項「+ 客戶有異議」按鈕不顯示）。
3. **M1_03 Walk-in 查詢**：車牌輸入 + 查詢按鈕已截到；「查得車主」綠橫幅未populate（測試車牌未對應到 walk-in lookup 條件），不影響功能存在性。
4. **B3 同車多工單警示橫幅**：需該車輛當下有 open RO 才會觸發，本輪未刻意建構該資料狀態，截到開立工單頁。
5. **角色對應**：腳本 `ACCOUNTS.manager（售後主管）` = `e2e-aftersales_lead`；主管工作台頁 / 售後稽核日誌需售後主管權限（純 SA 無權，屬人級 RBAC 設計）；集團/庫存稽核屬集團層，用 admin。
6. 所有截圖皆對**部署後正式站 URL**、以**真實非 admin 帳號**登入實拍，brand scope = Indian。
