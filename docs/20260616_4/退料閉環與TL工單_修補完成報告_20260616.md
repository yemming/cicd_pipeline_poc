## 動手前確認清單

- [x] **stock_items.status 可新增 return_pending**：✅ 可（check constraint 可擴充），但**最終未採用**。
  - 原因（delta）：出庫流程 `persistPick` 並未在 `stock_items.metadata` 寫 `source_addon_id` / `source_ro_id`，且部分出庫的 lot status 仍為 `available`（只扣量），無法可靠回溯「具體哪幾個 lot 該標 return_pending」。
  - 採用做法：退料閉環**不翻舊 issued lot**，改與現有 `parts-return-in` 完全一致 —— 取消時不回補、倉管確認收到時 **insert 一筆 `status='available'` 的 stock_item** 回補。退料明細來源改從 `repair_order_lines(kind='part')` 推導，不依賴出庫 metadata。結果完全符合測試斷言（取消後庫存不變、確認後 +N），且不需動 status constraint。
- [x] **system_settings.closing_time**：❌原本不存在（`settings` jsonb 為空）→ 新增 helper `getTodayClosingTime()` 讀 `settings.closing_time`，找不到 fallback **18:00 Asia/Taipei**（`src/domain/aftersales-settings.ts`）。
- [x] **TL 一車多工單規則已確認**：TL + 任何類型 = 允許（不告警）；TL + TL = 告警（warn，SA 確認後可並存）。實作於 `confirmRepairOrderAction`。
- [x] **return-in Tab B 不影響現有 Tab A**：✅ 現有領料退貨入庫看板原封不動成為 Tab A；新增 Tab B「售後退料確認」。
  - 註（delta）：原指令稱 Tab A 為「採購退貨」，實際上 `/parts/receipt/return-in` 既有內容是「**領料退貨入庫**」（採購退貨在 `/parts/purchase/returns`）。照原意圖：現有內容＝Tab A、退料確認＝Tab B。
- [x] **TL 轉入正式工單時 stock_issue_lines.ro_id 可更新**：結案 transfer 採「搬 `repair_order_lines.repair_order_id` 到目標工單」，庫存層不重複出庫（料已在技師手上，轉為正式工單耗用）。
