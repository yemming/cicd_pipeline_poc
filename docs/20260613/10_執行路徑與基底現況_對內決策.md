## 三、售後修護模組現況（這兩天的成果）

### 程式能做到什麼程度（主流程實測可走通）

預約 → 預檢 → 開立工單(RO) → 派工 → 維修領料(真扣庫存+成本過帳) → 追加項目(含退料反向) → 竣工複檢(含施工人不得自複檢) → 結帳收款(含折扣審批) → 關單(觸發 D+3 回訪 / 下次保養提醒) → 人車履歷更新。

這條主線**端到端可跑通且資料真實落地**（非假畫面）。

### 八個根本問題 / 45 必修的覆蓋

- **程式與業務邏輯**：約 **85–90%**。RP1-RP8（狀態機 / 電子簽名 / 退料反向 / 三層稽核 / 主管授權 / 跨頁串接 / 人車檔案 / 站內通知）皆已落地，部分甚至**超出設計稿**（折扣超限自動送審、30 分未批自動升級店長、施工技師不得自複檢的前後端雙重驗證、中途取消走主管審批等）。
- **黃金版設計細節忠實度**：約 **55%**（差距在 SVG 損傷點位圖、各種輔助 Panel、彩色時間軸視圖、跨模組串接橫幅等 UI 呈現）。

### 五個原先判定的「跨切致命發現」— 已全數修復並驗證

| 致命發現 | 狀態 |
|---------|------|

| ② 工單狀態機無任何護欄（可任意跳態、已關單可逆） | ✅ 已修（合法轉換白名單 + 終態不可逆 + 狀態歷史真表） |

## 四、為什麼「現在照設計稿大量補 UI」邊際效益有限

1. **剩餘工作的性質**：黃金版補完計劃約 32–50 人日，其中**逾半是 UI 忠實度**（Panel、時間軸視圖、SVG 圖、橫幅），不是業務邏輯缺口——業務邏輯主線已通。
2. **設計稿的定位**：黃金版 v3 是很完整的**設計基準**，但它是「對海德生需求的設計詮釋」，**尚未與海德生實際使用的表單與作業流程對齊**。
3. **風險**：在未對齊真實流程前投入大量人日復刻設計細節，可能出現「做得很精緻、但海德生實際不那樣跑」或「海德生紙本表單上的關鍵欄位反而沒涵蓋」的落差，造成返工。
4. **基底已強**：正因為資料庫 / 權限 / 開發模具 / 金流 / 發票 / 總帳這些底層都穩了，**我們具備「拿到真實需求後，快速、低成本地把對的功能補上去」的能力**——這正是先對齊、再施工划算的原因。

## 五、建議執行路徑（以完成度與工作推進為前提）

不糾結「跳過誰」的問題（海德生窗口可直接接觸），純粹以「把對的東西做完、少返工」為目標，建議分三步、可平行進行：

**第 1 步 ‧ 對齊真實流程（最小成本、最高資訊量）**
取得海德生目前實際使用的基本表單（預檢單、工單、結帳單、保固登記表）與作業流程，與黃金版設計、現有實作三方比對。這一步 1–2 次訪談即可，**直接決定 32–50 人日裡哪些是真需求、哪些可省**。

**第 2 步 ‧ 引導式測試 → 需求單 → 分批優化**
主流程現在 demo 得起來。以**引導式**走查（避免生用戶被細節雜訊干擾），把海德生真實反饋收斂成需求單，依價值與依賴排序分批落地。平台基底支援快速迭代。

**第 3 步 ‧ 與 Russell 同步、簽核設計基準**
Russell 維護的黃金版是寶貴的設計基準，全程同步進度、由其簽核；以海德生真實需求驅動優先序，黃金版作為設計參考與品質標準，兩者並行不衝突。

## 六、結論

平台基底（資料庫 / Helper 架構 / Spec-to-Feature / 電子發票 / POS / 總帳）已穩固，售後修護主流程與五大致命地基問題均已完成。**目前真正待補的，多為對一份尚未經真實流程驗證之設計稿的 UI 細節復刻。** 建議先以最小成本對齊海德生實際表單與流程，再以引導式測試收斂需求、分批優化，而非在對齊前投入大量人日於設計細節——這樣能把資源用在真正影響海德生使用體驗的地方，也讓黃金版設計基準發揮「校準參考」的最大價值。
