**自省 → 自驗 → 自記，缺一不可。**

**累積學習清單（截至2026-06-12）：**

| 編號 | 教訓 | 預防行動 |

## 🆕 模組檢查方法論（2026-06-12新增，每個新對話必讀）

**這是2026-06-12深度審查售後修護模組後，總結出的完整方法論。每次開啟新的「模組檢查對話」時，必須依照此方法進行。**

### 方法論概述

```
每個功能模組的完整檢查流程：

Phase A：建立主線劇本（1條黃金流程）
  ↓
Phase B：系統性走完所有岔路（B1-BN）
  ↓
Phase C：歸納故障點→對應根本問題
  ↓
Phase D：逐一討論解決方案（你我討論）
  ↓
Phase E：生成HTML修改清單（確認範圍）
  ↓
Phase F：生成Partner指令文件（逐條精確）
```

### Phase A：主線劇本格式

主線劇本選「最簡單、最常見的業務場景」，沒有任何例外。

**格式：**
```
場景描述：[角色]在[情境]下，[做什麼事]，[預期結果]。

Step 1｜[節點名稱]
  頁面：[HTML檔名]
  操作：[SA/技師/主管做什麼]
  支撐狀況：✅/⚠️/❌
  🚨 故障點[編號]：[問題說明]
```

**主線走完後統計：**
- 主線故障點數量
- 主線能否貫通（所有節點都能正常完成才算貫通）
- 原則：主線不通，所有岔路劇本都沒有意義

### Phase B：岔路劇本清單（售後修護模組已完成，其他模組待做）

**岔路的來源：**
1. 業界實務（從業界知識和同業經驗推導）
2. 客戶行為（客戶可能做出的各種非預期決定）
3. 系統邊界（資料不存在、狀態異常、多人同時操作）
4. 法律風險（需要留存憑證的情境）

**岔路格式（同主線）：**
每個岔路都要問：
- 業務規則是什麼？（業界標準/海德生規則）
- 系統哪些頁面需要參與？
- 目前的HTML設計能不能支撐？

**已完成的模組：**
- ✅ 售後修護模組：B1-B19共20個岔路，58個故障點，詳見《DealerOS_售後修護模組_重大修改方案_v1.md》

**待完成的模組：**
- ⬜ 銷售接待模組（對話B）
- ⬜ 庫存管理模組（對話C）
- ⬜ 客服CRM模組（對話D）
- ⬜ 集團管理模組（對話E）

### Phase C：故障點分類方法

**不用優先級燈號，所有故障點都是「真人測試前必須修復」。**

但可以按「根本問題」歸類，提高解決效率：
- 多個故障點同一根本原因 → 解一個等於解多個
- 根本問題討論完後，再展開成逐條Partner指令

**售後修護已歸納的8個根本問題（供其他模組參考）：**
1. 工單/流程狀態機設計不完整
2. 電子簽名機制缺失
3. 庫存退料反向流程缺失
4. 法律憑證與稽核記錄缺失
5. 主管授權機制設計不完整
6. 跨頁面資料串接斷鏈
7. 人車/客戶/車輛檔案與交易記錄的雙向同步缺失
8. 通知機制設計不完整

**其他模組很可能也有類似的根本問題，但細節不同。**

### Phase D：解決方案討論規則

**你我討論用：** 按根本問題討論，有效率
**Partner文件用：** 展開成每個故障點的逐條指令，精確無歧義

**每個解決方案必須包含：**
1. 業界背景（為什麼要這樣設計）
2. 設計定案（具體的UI/UX/業務邏輯）
3. Partner指令（API名稱、欄位、驗收標準）
4. 自測驗收標準（Partner AI Agent必須跑過才算完成）

### Phase E：HTML修改清單格式

```
需要修改的現有HTML：
  [頁面名稱] | [主要修改內容] | [對應根本問題]

需要新增的HTML：
  [新頁面名稱] | [功能說明] | [對應根本問題]
```

**修改原則：**
- 黃金版本HTML = 設計權威，Partner應以我們的設計為準
- Partner已實作的頁面（如技師工作台）→ 取得截圖對照，補強缺失功能
- 不等Partner回應，直接開始修改HTML

### Phase F：Partner指令文件格式

**每條指令的標準格式：**
```
【指令編號】[指令標題]

業界背景：
  [為什麼業界這樣做，附來源或業務邏輯]

設計意圖：
  [DealerOS為什麼這樣設計]

具體修改：
  前端：[具體UI變更]
  後端：[API名稱、方法、參數、回傳值]
  資料庫：[表名、欄位、類型]

自測驗收標準：
  ① [驗收項目1]
  ② [驗收項目2]
  ...
  所有項目通過才算完成，不接受部分完成。

不接受的回應：
  ❌ 只有截圖無API確認
  ❌ 說「已完成」但無佐證
```

### 3.3 台灣商業環境重要認知

**授權鏈定案（2026-06-12確認）：**
```
門店授權鏈：售後主管 → 店長（終點）
不往集團層傳遞
集團層：唯讀，只看數字，不介入門店授權決定

適用範圍：海德生授權經銷商（非直營）
  即使海德生自營店，店長也是盈虧自負責任制
  系統不參與門店與集團之間的私下協議
```

### 3.4 IN付款（免費工單）的正確記錄方式

```
billing_amount = [實際成本]（必須記錄）
customer_paid = 0（客戶實收）
internal_cost = [實際成本]（門店承擔）
payment_type = 'IN'

原因：
  1. 財務正確性（帳面毛利不能虛高）
  2. 品質管控（返工/免費重工成本累積是品質指標）
  3. 稽核防弊（防止把應收費工單改成IN送給客戶）
```
