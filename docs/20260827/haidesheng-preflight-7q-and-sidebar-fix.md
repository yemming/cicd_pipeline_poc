**現況查證**：`app_admins` 表目前只有 `email / granted_at / granted_by / notes` 四欄，**沒有任何 brand 範圍限制欄位**——David 跟 Ming、consultant01 是同一張表、同一套全域權限，技術上確實能看到碩文（Ducati）全部資料，跟文件描述一致。

**方案評估**：

- 方案B（`app_admins` 加 `brand_scope` 欄位）：改動小很多，只需在既有 admin 判斷邏輯多一層範圍檢查，能趕在下週前完成。

**⏸️ 尚未實作，等 Ming 拍板選 A 或 B**。David 帳密目前尚未交付給他本人，符合文件要求的時間順序。

### Q1：18人角色能否自助調整

**現況查證**：DB 確認 18 位海德生/Lambretta/Polaris 人員的 `role_id` 全部仍是 `viewer`，尚未有人被升級過，跟文件描述一致。

**這次順帶發現並修復的問題**：實際用測試帳號登入後，**左側選單完全是空的**（詳見下方「二、Sidebar 修復」）。這不是權限機制的問題，是海德生三個品牌（`indian-hds` / `lambretta-hds` / `polaris-hds`）的導覽資料（`nav_nodes`）從一開始就沒有建立，只有集團管理的空殼——這件事不在原七題範圍內，是驗證過程中意外抓到的地基缺口，已一併補上（見下段）。

補上導覽後，「David 自助改角色」這條路徑的畫面前提才成立；但**實際用 David 帳號走一次登入→搜尋→調整角色→儲存的操作，我方尚未親自跑過**，建議下週實測時第一件事排這個，卡住立刻回報。

### Q2：財務角色缺口

### Q3：1,716筆無品牌零件

**現況查證**：匯入腳本 `scripts/etl-haidesheng/import-parts.mjs` 遇到品牌判不出來直接整批跳過、不寫入 DB（`skippedNoBrandCount: 1716`，DB 目前 `brand_id is null` 筆數確認為 0）。

三步驟判斷合理，同意採一次性小腳本做法（不做成正式 UI）。**待 J200 正式車型資料確認後才能動工**，目前無阻塞。

## 二、Sidebar 空白修復（驗證過程中發現並當場處理）

### 問題

真人拿測試帳號（viewer 角色、scope=海德生品牌）登入正式站，左側模組選單完全空白，只有一個「集團管理」佔位。

### 根因

`nav_nodes` 是全站導覽的 Single Source of Truth（`src/lib/modules.ts` 只是 fallback）。查證發現 `indian-hds` / `lambretta-hds` / `polaris-hds` 三個品牌各自只有 **5 筆** `nav_nodes` 資料（集團管理的空殼結構），從沒人幫這三個品牌建過任何實際業務模組的導覽節點。**這不是權限被擋，是地基從沒鋪過。**

### 處理方式

比對 `indian` 品牌現役（`is_active=true`，排除舊版已廢棄分支）的四棵導覽子樹：

| 對應模組 | 來源（indian 品牌現役節點） | 頁面數 |
|---|---|---|
| 營運 | 庫存管理（parts） | 101 頁 |
| 銷售 | 銷售接待 | 27 頁 |
| 客服 | 客服管理 | 14 頁 |
| 維修 | 售後修護（aftersales） | 38 頁 |

整棵複製（含 parent_id 重新對應）到 `indian-hds` / `lambretta-hds` / `polaris-hds` 三個品牌底下，`indian` / `ducati` 原始資料未被觸碰。

### 變更範圍確認

- ✅ 做了：三個海德生品牌各補上 214 筆 `nav_nodes`（4 個模組、含全部子頁），總筆數從 5 → 219
- ❌ 沒做：沒有動 `role_permissions` / 權限矩陣——這幾個模組底下的頁面目前對 `viewer` 角色是開放可見的，尚未依角色分級顯示操作權限（等 Q1/Q2 拍板後才會分級）
- ❌ 沒做：沒有動「集團管理」底下原有節點、沒有動任何其他品牌的 `nav_nodes`

### 執行紀錄

透過 `mcp__supabase__execute_sql` 直接在 Supabase Cloud 執行一段 PL/pgSQL（無獨立 migration 檔，本專案 schema 變更向來走 Cloud 手動 apply）：對 `indian` 品牌四個現役 level-1 節點做遞迴複製，`brand_id` 換成三個海德生品牌，parent_id 用暫存映射表重新對應。無 DDL、純資料寫入，可用 `DELETE FROM nav_nodes WHERE brand_id IN (...) AND created_at > '2026-08-27'` 之類條件回滾（未執行回滾，僅供備忘）。

### 驗證與證據

- SQL 驗證：三品牌 `nav_nodes` 筆數皆為 219（5 + 214），`level=1` 六筆（含 4 新模組 + 原本的集團管理/零件營運），parent_id 鏈完整無斷裂
- 畫面驗證：Ming 用測試帳號重新整理後回報「畫面還可以」，四個模組已可見可點

## 二之二、追加修復：David 帳號漏開「系統設定」模組（2026-08-27 當天追加）

上面「二、Sidebar 修復」只補了業務四模組（銷售/客服/維修/庫存），**漏掉 David 真正需要的「系統設定」模組**——`app_admins.notes` 已明確記載 David 被授權的目的是「海德生總代理管理員 — 授權自行調整18人角色指派」，但他真正要用的 `/admin/rbac`（權限管理）入口沒開出來，導致他登入後模組跟其他人一樣少，看不出自己有 admin 身份。

⚠️ **注意**：這個模組底下混了幾個 `indian` 品牌自己也還沒清掉的舊版 dead link（`is_active=false`，例如 `/settings/org` 組織架構），比照原本 indian/ducati 現況原樣搬過去，沒有額外清理，屬於既有技術債，不在本次任務範圍內。
