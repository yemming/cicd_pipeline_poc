## ⛔ 強制核查規則（最優先，凌駕一切）

**在任何對話中，只要涉及以下判斷，Claude必須停下來核查原始資料，不得直接引用任何文件描述：**

| 觸發情境 | 必須執行的動作 |
|---------|-------------|
| 判斷「某功能存不存在」 | `unzip` 原始HTML，親眼確認頁面結構和Tab內容 |
| 判斷「某頁面缺少什麼」 | 同上，不得引用舊版分析文件的❌清單 |
| 生成任何對外文件（評估/清單/說明） | 先確認每一個描述都有原始依據，標注來源 |
| 對Partner或客戶的工作做出評價 | 先讀實測回填文件或上版報告，再說 |
| **審視任何業務流程頁面** | **必須扮演真實使用者走一遍完整工作場景，不只看單一頁面** |

**根本原因（必須記住）：**
- DealerOS的設計哲學是「相關功能整合在同一頁面的不同Tab」，不是每個功能一支獨立HTML
- 正確的評估問題是：「這個業務場景，使用者有沒有地方可以完成它？」
- 錯誤的評估問題是：「這個功能有沒有自己的HTML頁面？」

**往後的承諾：**

**不等Russell主動提出，Claude自己發起這個步驟。**

### 承諾二：審視頁面時，第一個問題永遠是「使用者能做到應該做的事嗎？」

不是「這頁長什麼樣子」，不是「Tab名稱是否正確」，不是「顏色是否符合設計規範」。

**第一個問題永遠是：**
> 「使用者來這頁，是要做什麼？現在能做到嗎？」

2026-06-07的07B費率設定頁教訓：Claude第一眼看到截圖，注意到Tab名稱被簡化、麵包屑路徑奇怪、警示橫幅有debug文字——但完全沒有注意到最核心的問題：費率欄位是唯讀的，使用者完全無法設定費率。

### 承諾三：跨頁面流程必須驗證資料帶入

任何涉及多個頁面的業務流程，Claude必須驗證：

1. 上一頁的確認按鈕，有沒有真正寫進DB？（不只是Toast）
2. 下一頁有沒有正確帶入上一頁的所有必要資料？
3. URL或Session中有沒有正確傳遞關鍵ID（如pi_id、ro_id）？

**自問：「使用者在這個流程中，有沒有被迫重新填寫任何已填過的資料？」**

## ⛔ 閉環管理（核心工作原則）

**自省 → 自驗 → 自記，缺一不可。**

| 層次 | 核心問題 | 具體行動 |
|------|---------|---------|
| 自省 | 我真的做對了嗎？ | 完成任何工作前，主動回頭檢查，不等別人指出問題 |
| 自驗 | 我有沒有漏掉什麼？ | 執行具體驗證步驟，不靠感覺說「應該沒問題」 |
| 自記 | 這次的教訓是什麼？ | 發現問題後記錄根本原因和預防措施，讓同樣錯誤不再發生 |

**累積學習清單（截至2026-06-09）：**

| 編號 | 教訓 | 預防行動 |
|------|------|---------|
| L-001 | 設定頁的編輯功能在React化時容易遺失（07B費率設定頁） | 所有「設定」類頁面完工後，必須實際點擊每個輸入欄位確認可編輯，並測試儲存按鈕是否存在且有效 |
| L-002 | 跨頁面業務流程的資料傳遞在React化時容易斷鏈（預檢單a→b→c） | 完成多步驟業務流程後，必須從第一步走到最後一步，確認每一步確認按鈕有寫DB、下一頁有帶入資料、URL有傳遞關鍵ID |
| L-003 | 確認按鈕只顯示Toast≠功能完成 | 每個確認/送出/儲存按鈕完工後，必須驗收：後端API是否真的被呼叫、API回應狀態是否正確、頁面是否有正確反應 |
| L-004 | 增項閉環的漏斗數據缺口：拒絕按鈕只記錄「拒絕了」，不採集「為什麼拒絕」，導致漏斗分析永遠殘缺（04_追加項目記錄案例） | 所有涉及「客戶說不」的業務節點，必須採集結構化原因：固定標籤（必填）+自由文字（選填）。自問：「這個拒絕的數據，主管事後能用來分析和改善嗎？」 |
| L-005 | 以「頁面為單位」審視設計，忽略「人的連續體驗」 | 每個模組完成後，必須以角色扮演方式走完整工作日場景 |

## 第四層：工作方式規則（v8延續+新增）

### 4.1 每個模組的正確工作順序

```
1. 上網收集業界資料與同業最佳實務
2. 直接 unzip 掃描原始 HTML（不靠任何舊文件推論）
3. 與 Russell 討論確認
4. 取得明確同意後才動手
5. 完成 HTML 修改/新增
6. 【新增】主動提出角色扮演，走一遍完整工作日場景
7. 確認無流程斷點後，生成 MD 異動說明文件
8. 生成場景驗證清單 .docx
9. 全部產出一次 present，文件+HTML 不分批
```

### 4.2 不能做的事

```
❌ 引用舊版分析文件的❌清單而不核查原始頁面
❌ 跳過討論直接動手修改 HTML
❌ 場景驗證清單寫在 HTML 修改之前
❌ 產出後只 present 部分（文件+HTML 必須一起）
❌ 金額單位用 ¥，一律用 NT$
❌ 對外文件中出現未核查過的「缺口」描述
❌ 模組完成後不主動提出角色扮演審視（新增）
❌ 只看單一頁面，不審視跨頁面的資料流動（新增）
❌ 確認按鈕只有Toast就認為功能完成（新增）
```
