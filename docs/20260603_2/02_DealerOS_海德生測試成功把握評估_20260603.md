## 一、測試類型定義（先對齊再評估）

| 類型 | 說明 | 判斷基準 |
|------|------|---------|
| **A型　功能展示測試** | Russell主導帶著客戶走流程，數字可以是假資料，客戶看的是「這符不符合我的業務流程」 | 核心頁面React化、流程邏輯正確即可 |
| **B型　真人實測（UAT）** | 海德生員工用自己的角色帳號獨立操作，輸入真實資料，看到真實結果 | RLS、角色帳號、示範資料、跨模組串接缺一不可 |

## 二、06/02 前進度的評估

### 整體把握：A型 60%　／　B型 15%　／　**綜合 30–40%**

**能成的原因（已有底氣的部分）：**
- 銷售接待、客服CRM、售後工單核心流程已從靜態HTML升級為真實React + Supabase DB
- 15/15銷售接待路由、13/13客服管理路由 Playwright 全綠
- 電子手卡、試乘試駕、工單建立等關鍵動作已真實寫入DB

**會失敗的原因（致命缺口）：**

| 缺口 | 狀態 | 對測試的衝擊 |
|------|------|------------|
| GRP20 RLS完全未設定 | ❌ 未做 | 任何帳號能看到所有資料，資料隔離形同虛設 |
| 各角色帳號未建立 | ❌ 未確認 | 沒有角色帳號，無法做跨角色協作測試 |
| 測試示範資料未種入 | ❌ 未做 | 海德生員工第一次登入看到空白系統 |
| nav_nodes目錄搬移未確認 | ❌ 未確認 | 目錄結構跟規範 v2.0 不符，RS_INV02/03 仍在錯誤位置 |
| PDI工單執行未對海德生隱藏 | ❌ 未確認 | 海德生（授權經銷商）看到不應出現的功能 |
| 跨模組自動觸發鏈普遍未做 | ❌ 多處斷鏈 | 工單完成→CRM沒反應，流程斷點讓客戶困惑 |
| 電子簽名為假動作 | ❌ canvas未實作 | 預檢/結帳簽名點了沒反應 |

**結論：06/02 前，B型真人實測幾乎不能做。A型展示勉強可以，但因為示範資料不足、目錄結構未對齊，能留下的印象相當有限。**

### 06/03 後仍存在的缺口（為什麼還是65–70%而非更高）

#### 🔴 缺口一（扣 15%）：GRP20 RLS + 角色帳號 — 尚未完成

這是B型測試的地基。沒有這個，一切都是空中樓閣。

```
目前狀態：Supabase RLS 只在2張表（維修工單+績效數據）試點
尚未完成：全系統197張表的Row Level Security
影響：海德生業務員登入後能看到其他業務員的客戶資料
     → 客戶會問「這樣個資怎麼保護？」直接動搖信任
```

**最低要求（測試前必須）：** 核心5張表完成RLS
`sales_handcards` / `work_orders` / `customers` / `call_tasks` / `inventory`

#### 🟡 缺口二（扣 10%）：跨模組自動觸發鏈 — 普遍未做

這是客戶感受「系統是活的」的關鍵，現在大多數流程在跨模組時就斷掉了。

| 觸發鏈 | 狀態 | 客戶測試時的感受 |
|--------|------|--------------|
| 工單關閉 → D+3/D+7電訪任務自動建立 | ❌ 未做 | SA結帳完，CRM工作台沒反應 |
| 手卡儲存 → 自動新增到客戶基盤 | ❌ 未做 | 新潛客不出現在CRM清單 |
| 交車完成 → 售後客戶檔自動建立 | ❌ 未做 | 銷售和售後資料斷鏈 |
| 休眠狀態自動降級cron | ❌ 未做 | 休眠客戶名單不準確 |
| LINE / SMS 真實推播 | ❌ 未做 | 按了「發LINE通知」客戶沒收到 |

> ⚠️ 注意：這些缺口在測試時**可以口頭說明「正在開發中，預計X月完成」**，不會讓測試立刻失敗。但RLS缺口無法靠口頭解釋帶過。

## 五、要從 65–70% 提升到 90%，還需要做三件事

優先序如下，**必須按順序，不建議跳步驟**：

### 🔴 第一優先：GRP20 RLS + 角色帳號（預估工作量：3–5天）

```
1. GRP20 org_mode=3 設定串接（海德生三層架構）
2. 核心5張表 Supabase RLS：
   - sales_handcards（業務員只看自己的）
   - work_orders（SA只看被指派的；技師只看自己工單）
   - customers（依角色和門店隔離）
   - call_tasks（CRM專員看全部；RS/SA只看自己）
   - inventory（倉管看全部；SA只看維修領料）
3. 建立測試角色帳號：
   店長×1 / 業務員RS×2 / SA×1 / 倉管×1 / 技師×1
```

### 🔴 第二優先：種入海德生示範資料（預估工作量：1–2天）

```
- 車輛主檔：Indian Scout Bobber / Chief Vintage / FTR Sport 各2台
- 客戶資料：10–15筆示範客戶（非真實個資，但有真實感的名字）
- 服務套餐：Indian保養套餐 6000/10000km
- 工時費率：Indian Motorcycle 費率設定
- 庫存品項：20–30個常用零件（機油/濾芯/煞車片等）
```

### 🟡 第三優先：nav_nodes對齊規範v2.0（預估工作量：半天）

```
- 導覽頁全部 is_active=false
- RS_INV02/03 搬至集團管理
- CRM05A/05B 搬至主管監看區
- PDI工單執行對海德生設 is_active=false
- 基礎設定/系統設定群組預設收合
```

**完成以上三項後，可以安排一次有品質的 A型展示（你主導，每人用自己角色帳號，看到正確資料範圍），成功把握可提升至 85–90%，足以推進正式簽約討論。**

## 六、Russell 建議的測試策略

不要急著做 B型 全模組真人實測。建議分兩個階段：

**Phase 1（現在可以安排，完成上述三件事後）：A型有品質展示**
- Russell主導，帶2–3位海德生代表走核心場景
- 核心場景：①接待手卡→試乘→報價成交；②SA預檢→工單→結帳；③店長看漏斗看板
- 每人用自己角色帳號登入，看到正確的資料隔離
- 目標：讓海德生確認「這個系統符合我們的業務流程」→ 推進到合約談判

**Phase 2（合約簽署後，準備正式上線前）：B型完整UAT驗收**
- 海德生員工獨立操作，逐場景完成所有131個場景驗收
- 跨模組觸發鏈在此時完成串接
- 真實個資匯入，系統正式運作
