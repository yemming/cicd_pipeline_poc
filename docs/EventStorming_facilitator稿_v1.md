# Ducati DealerOS — Event Storming Facilitator 流程稿（v1）

**用途**：Ming 主持、Russell 出席的 2 小時 Event Storming workshop。讀完此文即可開跑，不需另外備課。
**目標產出**：一張領域事件地圖（40–60 個橘色事件）+ 4–6 個 bounded context + 一份凍結至 +14 天的 schema baseline。

## §1 兩小時 minute-by-minute 流程

### Phase 1｜開場與規則（00:00–00:10，10 分鐘）

**唸開場逐字稿（§2）→ 解釋顏色卡 → demo 一張範例 sticker。**

範例 sticker：在「銷售前段」區塊貼一張橘色 `車主已抵達展廳`，下方貼黃色 `車主`、`接待 SA`，下方貼藍色 `識別來客身分`。告訴 Russell：「就是這樣，您負責想場景、講出來，我負責分顏色。」

### Phase 2｜Chaotic Exploration（00:10–00:50，40 分鐘）

**規則：只貼橘色，不排序、不分類、不爭論。**

引導語每隔 5 分鐘換一個切角，避免冷場：

| 分鐘 | 引導問題 |
|------|---------|
| 00:10 | 「請從一位**新客**第一次進店開始講起 — 從他進門那一刻到離店為止，都發生了什麼？」 |
| 00:15 | 「現在切到一位**老客戶換購**，跟新客有什麼不一樣的事件？」 |
| 00:20 | 「客戶已簽訂單之後到正式交車中間，**內部跨部門**發生了哪些事？」 |
| 00:25 | 「車主第**一次**回廠保養，從進門到離廠，發生哪些事？」 |
| 00:30 | 「**異常情境**：YouTech 索賠、車主拒絕修、戰敗結束 — 這些少見但會發生的事件？」 |
| 00:35 | 「**主管視角**：每天下班時、每週五複盤時，發生了哪些事？」 |
| 00:40 | 「**外部系統觸發**：YouTech 核准、Line 推播失敗、原廠召回通知 — 這類事件？」 |
| 00:45 | 「最後一輪：**任何您想到漏掉的**，哪怕跟以上都沒關聯，都貼上去」 |

**facilitator 的手要快**：Russell 講一句你貼一張，不要等他講完三段才動手 — 邊講邊貼能看見的視覺累積會讓他持續產出。

**目標**：這 40 分鐘累積 **40–80 張橘色 sticker**。低於 30 張代表 Russell 太矜持（追問細節）；高於 100 張代表你在重複貼（合併）。

### 休息（00:50–01:00，10 分鐘）

關鏡頭、各自走動。**這是 Ming 偷時間整理的關鍵 10 分鐘** — 趁 Russell 不在，把明顯重複的橘色 sticker 疊到一起、把貼錯區塊的拖到對的區塊、把口語化的 sticker 改成過去式（「會推播 Line」→「Line 推播已發送」）。

### Phase 3｜時間軸排序（01:00–01:30，30 分鐘）

**規則：每個區塊內，把橘色 sticker 由左至右依時間順序排列。**

引導語：

> 「現在我們進入排序階段。每個區塊裡的事件，請您按照**真實業務發生的先後**告訴我順序。我來移動 sticker。如果兩個事件可以同時發生，就上下並排。」

- 一個區塊一個區塊處理（銷售前段 → 銷售後段 → PDI → 售後接車 → 售後追蹤）
- 每個區塊處理完，**問 Russell 一句**：「這條時間軸有缺漏嗎？有沒有事件夾在中間我們忘了？」漏掉的補貼新 sticker
- 排序時自然會發現「這兩個其實是同一件事」 → 合併
- 也會發現「這個事件後面還跟著一串連鎖反應」 → 把 policy（紫色）加進去：「**當** X 事件 **則** 自動觸發 Y」

**目標產出**：5 個區塊、每個區塊 8–15 張橘色，共約 50–60 個 unique events，順序明確。

### Phase 4｜Hot Spots & Aggregates（01:30–01:50，20 分鐘）

**步驟一（10 分鐘）— 標 hot spots**：

> 「現在快速掃過全板，凡是您覺得**還沒想清楚**、**有爭議**、或**這事該誰做還不確定**的事件，旁邊貼一張紅色 sticker。」

紅色 sticker 是黃金 — 那是**真正需要 Ming 跟 Russell 進一步討論的點**。本次 workshop 不在現場解決，但會在凍結卡片裡列為「14 天內要決議的事項」。

**步驟二（10 分鐘）— 圈 aggregates**：

> 「最後一步。請您看每一群連續發生的事件 — 這群事件**操作的是同一個東西嗎**？例如『車主已簽名』『追加項目已新增』『QA 已通過』『取車通知已發送』 — 這些都是針對**同一張 RO 工單**的事件對吧？我們把這群圈起來，給它一個名字。」

用 Miro 的方框工具圈起來，命名（例如 `RepairOrder`、`PreInspection`、`SalesCard`、`DropoffCase`）。**這些方框就是你的 aggregate，也就是未來的 table 主檔**。

**目標產出**：6–10 個 aggregates 用方框圈出來，每個有名字。

### Phase 5｜凍結合約 + 下一步（01:50–02:00，10 分鐘）

**唸結束逐字稿（§3）→ 填寫凍結合約 frame → 約下次會議。**

填寫範例：

```
本次 workshop 鎖定的事件 baseline：53 個
Aggregates：8 個（Customer / Vehicle / SalesCard / PreInspection / RepairOrder / DropoffCase / WarrantyClaim / PDIRecord）
凍結至日期：2026-05-12
簽核：Russell（口頭）／ Ming（口頭）
凍結期內紅色 hot spots（7 張）：5/5 前由 Ming 起草解法、5/8 線上 30 分鐘評審
```

## §2 開場逐字稿（10 分鐘，照念）

> Russell 您好，謝謝您撥這 2 小時。
>
> 在開始前我想花 3 分鐘解釋為什麼今天要做這個。
>
> 我們從 v1 改到現在已經七、八版，但每次您丟一個新場景進來，我這邊的資料庫結構就要動一次，這是工程的常態 — **不是您的問題，是我們之前沒有用對方法收斂**。
>
> 您 30 年汽機車業的經驗灌進來的內容，本來就是場景化、有時序的。我這邊一直用「資料庫表格」去接，等於用靜態的容器接動態的水流，當然會溢出來。
>
> 所以今天要做的事情叫 **Event Storming**，2013 年義大利人 Alberto Brandolini 發明，DDD 圈現在的標準做法。它的核心想法只有一句話：
>
> **「先把已經發生過的事件全部攤開，再從事件群聚反推資料結構。」**
>
> 您負責回憶業務上**真實發生過的事件**，我負責把這些事件貼到牆上、排時間軸、圈出資料邊界。
>
> 兩個遊戲規則：
>
> **第一**，事件用**過去式**描述。
> 不是「我覺得系統應該要有個功能讓 SA 簽名」，而是「**SA 已簽名**」。
> 不是「按鈕點下去推播 Line」，而是「**Line 推播已發送**」。
> 過去式很重要，因為過去式逼我們想「**已經發生**的事」，這種事情不會因為畫面改了就變動。
>
> **第二**，沒有對錯、不挑刺。您想到什麼貼什麼，包括很少見的、異常的、戰敗的、跨部門的。我這邊不會打斷您 — 我只負責邊聽邊貼。
>
> 這個板上有五個區塊，從左到右是：銷售前段（接待到談判）、銷售後段（成交到交付）、PDI 跨部門、售後接車（預檢到簽單）、售後追蹤（取車到閉環）。
>
> 顏色我先講，等等您不用記，我會幫您分：
> - 橘色是事件（您主要產出這個）
> - 黃色是「誰做的」（SA、車主、技師…）
> - 藍色是命令（觸發事件的動作）
> - 紫色是規則（自動觸發的 policy，例如「拒絕→自動建失銷追蹤」）
> - 綠色是看板（read model）
> - 粉紅是外部系統（YouTech、DCS、Line）
> - 紅色是「還沒想清楚」 — 您可以隨時舉手說「這個我不確定」，我貼紅色
>
> 我們先做 40 分鐘 chaotic 階段 — 您想到什麼就講什麼，**不用按時間順序、不用按區塊**，跳著講都行。第一個事件我來示範...
>
> （示範範例 sticker，然後說：）「好，輪到您了。從一位新客第一次進店開始 — 他進門的那一刻，**第一件已經發生的事**是什麼？」

## §3 結束逐字稿（10 分鐘，照念）

> Russell，我們今天做了三件事：
>
> **第一**，把您腦中的業務情境攤成 53 個事件 — 兩條動線從來客到閉環全部覆蓋，沒有遺漏。這在過去七、八版我們從來沒做過。
>
> **第二**，這 53 個事件圈出 8 個資料邊界 — Customer、Vehicle、SalesCard、PreInspection、RepairOrder、DropoffCase、WarrantyClaim、PDIRecord。**這 8 個就是未來資料庫的主檔**，未來只要您新想到的場景能 map 進這 8 個邊界裡某幾個事件，我這邊資料庫不需要動 — 我們就能持續把畫面做好、把流程串通。
>
> **第三**，我們抓出 7 個 hot spots — 這 7 件事我們今天**故意沒解決**，因為當下沒共識硬定就會錯。我會在 5/5 前針對每一張紅色 sticker 起草一個解法（A 案 / B 案各自利弊），5/8 我們線上 30 分鐘把這 7 件決掉。
>
> 接下來兩週是 **schema 凍結期**，到 5/12 為止：
>
> - 您隨時想到的新場景請繼續講 — 但**請先試著用既有 8 個 aggregate + 53 個事件來描述**
> - 90% 的時候會發現「這就是現有事件 + 新看板」，這種情況我下午就能改畫面
> - 真的 map 不上的（也就是真正的新事件），我們就標起來等下一場 Event Storming 再加 — 不在凍結期內動表結構
>
> 這個紀律執行 2 週，您會發現我們的進度比過去七、八版加總起來還多，因為**改畫面快、改 schema 慢**，我們之前一直在改慢的東西。
>
> 今天的板我會匯出 PNG 放到 BrainDump 卡片，連同凍結合約一起。下一場 Event Storming 訂在 5/19，到時候我們再加新事件、評估要不要拉新 aggregate。
>
> 辛苦了，謝謝您今天 2 小時。

## §4 facilitator 應對手冊（卡關時翻這頁）

### 4.1 Russell 進入「設計模式」 — 開始畫畫面

**症狀**：「這個按鈕應該放右下角」「這個欄位應該下拉」

**對應**：「停一下 — 這是設計畫面的事，今天我們聚焦在『事件層』。畫面我們之前已經有 4 個原型，等事件確定後再回頭調畫面 1 小時就搞定。**現在這個畫面背後，已經發生的事件是什麼？**」

### 4.2 Russell 進入「規格模式」 — 開始定義欄位

**症狀**：「客戶資料要包含姓名、電話、Line ID、生日、住址、職業...」

**對應**：「這是 schema 細節，先別管。我們先確定『**客戶資料已建立**』這個事件存在，欄位等 14 天凍結期我來訂草案、您 review。」

### 4.3 Russell 跨域跳躍 — 從售後突然跳到財務

**症狀**：「對了講到這裡，財務那邊應該要...」

**對應**：「先記下！」 — 馬上貼一張 hot spot 紅色 sticker 寫「財務 context — 待釐清」，立刻拉回原區塊。**不要打斷他的流，但也不要跟他跳走。**

### 4.4 兩個事件描述的是同一件事

**症狀**：板上有「車主簽完字」和「客戶簽名完成」

**對應**：當場合併，並問 Russell：「這兩張說的是同一件事吧？我們統一叫『**車主已簽名**』可以嗎？」 — **建立 ubiquitous language（共通語言）這個瞬間最寶貴**。

### 4.5 卡住 5 分鐘沒新事件

**症狀**：Russell 想不出來、眼神放空

**對應**：切角度問。從「正常路徑」切到「異常路徑」（戰敗、退訂、爭議），或從「個人視角」切到「主管視角」，或從「進廠那天」切到「進廠 30 天後」。**異常路徑通常會炸出 10 張 sticker。**

### 4.6 Russell 想否定剛才的 sticker

**症狀**：「等等，我剛才那個說錯了，刪掉」

**對應**：「不刪喔 — 業務上**真的發生過**的事不能刪，只能 mark 為 deprecated 或標 hot spot。如果您現在想到更精確的描述，我們新增一張在旁邊，原本那張保留為歷史。」

## §6 成功的判斷標準

兩週後（5/12）回頭看，如果以下三件事都成立，這場 workshop 就算成功：

1. **Russell 至少丟了 5 個新場景**，但我們**完全沒動 schema** — 全部用既有事件 + 新看板實作完
